# AGENTS.md — mandatory instructions for Codex

This repository is controlled by an architect-led workflow. These instructions apply to all implementation agents working anywhere in this repository.

## 1. Roles and authority

The project architect / technical lead owns:

- architecture;
- data contracts;
- source-connector strategy;
- scope and phase boundaries;
- task decomposition;
- acceptance gates;
- decisions about dependencies, storage and interfaces;
- approval of new market families or sources;
- final review of implementation changes.

Codex is the implementation agent. Codex may:

- write code for an explicitly assigned task;
- write/update tests required by that task;
- run local read-only diagnostics and approved source probes;
- refactor inside the assigned boundary when behavior and contracts remain unchanged;
- report defects, uncertainty and architectural risks.

Codex must **not** silently:

- redefine architecture;
- expand scope;
- add automated betting/order placement;
- add a new external source/provider;
- change canonical schemas or arbitrage formulas;
- change settlement compatibility rules;
- weaken tests or acceptance gates;
- introduce VPN/geoblock/anti-bot bypass mechanisms;
- use credentials or accounts not explicitly provided by the owner;
- commit secrets, cookies, browser profiles or raw credentials.

When an implementation task reveals that an authority document is wrong or incomplete, stop the affected design choice, document the finding, and request an architect decision. Do not invent a replacement architecture.

## 3. Repository hygiene before any write

Before editing:

1. run `git status --short`;
2. record current branch and HEAD;
3. `git fetch`;
4. verify the task is based on the intended remote HEAD;
5. do not discard unrelated local changes;
6. do not force-push;
7. create/use the branch specified by the task. If none is specified, use `codex/<phase>-<short-task>`.

If the local tree contains unexpected changes, report them before overwriting anything.

## 4. Implementation defaults

Unless an authority document or task overrides them:

- Python async backend;
- UTC timestamps at external/data boundaries;
- typed models;
- deterministic parsing/normalization;
- dependency injection around external connectors;
- no source-specific fields leaking into canonical domain objects unless explicitly modeled as provenance;
- event-driven recalculation in the hot path;
- configuration through environment/config files, never hard-coded secrets;
- Windows-first scripts must be PowerShell-compatible;
- source raw payloads must be redacted before persistent logging where credentials/session data could appear.

## 5. Source acquisition rules

This project begins as read-only research.

Allowed implementation work includes:

- public Polymarket market-data REST/WebSocket clients;
- browser-based observation of pages the owner can normally access;
- Playwright/CDP diagnostics that observe network traffic generated by that browser session;
- approved third-party odds APIs after an architect decision;
- parsing and normalizing obtained public/read-only data.

Not allowed without a new architect decision and explicit owner authorization:

- automated wager placement;
- account automation intended to place wagers;
- bypassing access controls, CAPTCHA, geoblocks, authentication or anti-bot mechanisms;
- replaying private authenticated endpoints outside the authorized browser/session context;
- evading rate limits;
- using a source in a way known to violate the applicable operator terms.

If a source blocks access, record `BLOCKED` with evidence. Do not build an evasion workaround.

## 6. Market-safety rule

Never match markets from text similarity alone.

A match requires the same:

- event/participants;
- competition/context where relevant;
- start-time identity within configured tolerance;
- market family;
- side/outcome semantics;
- line value;
- period/scope (full match, set, map, round, etc.);
- overtime/extratime treatment;
- settlement/void/refund rules to the extent required by the family;
- other family-specific rule signature fields.

When rules cannot be verified, state must be `UNVERIFIED` or `REJECTED`, never `MATCHED`.

## 7. Tests are part of implementation

A task is not complete because code runs once.

Required as applicable:

- unit tests;
- parser fixtures;
- normalization contract tests;
- replay tests for captured source samples;
- matcher positive and negative cases;
- arbitrage formula tests;
- stale-data tests;
- reconnect/idempotency tests;
- storage migration tests;
- integration tests using mocks/fixtures before live probes.

Never delete/skip/fuzz a failing test merely to obtain green CI.

## 8. Live-probe discipline

A live probe must be explicitly part of the task. Each live probe must record:

- source;
- local UTC start/end;
- endpoint/page class (secrets removed);
- purpose;
- request/event counts where practical;
- result: PASS / PARTIAL / BLOCKED / FAIL;
- relevant sample artifact location;
- whether any authentication was used;
- observed limitations.

Do not turn a diagnostic probe into an uncontrolled continuous collector.

## 9. Task completion / handoff

Before claiming completion:

1. run the required test commands;
2. run formatting/lint/type checks specified by the task;
3. inspect `git diff`;
4. verify no secrets/private runtime data are included;
5. update project state only if the task explicitly requires it;
6. commit with a meaningful message;
7. push without force;
8. read back the remote commit/tree when instructed;
9. report exact commit SHA, files changed, tests and unresolved issues.

A good handoff distinguishes:

- implemented;
- tested;
- live-verified;
- not tested/live-verified;
- blocked;
- deferred.

## 10. Definition of “done”

Only the architect accepts a phase. Codex may report `IMPLEMENTATION_COMPLETE`, but must not self-declare an architectural phase accepted unless the task explicitly delegates that gate.
