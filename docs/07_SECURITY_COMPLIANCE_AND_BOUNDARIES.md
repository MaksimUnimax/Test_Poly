# 07 — Security, Compliance and Operational Boundaries

## 1. Purpose

This project handles external market data, browser sessions and notification credentials. Security and access boundaries are part of correctness.

The MVP is a read-only research scanner. It does not automate wagering.

## 2. Prohibited implementation in current scope

Do not implement:

- automatic sportsbook bet placement;
- automatic Polymarket order placement;
- account login automation for wagering;
- CAPTCHA solving/bypass;
- geoblock bypass;
- anti-bot evasion;
- proxy rotation intended to defeat source restrictions/rate limits;
- credential harvesting;
- replay of private authenticated endpoints outside an explicitly authorized session/use case;
- hidden persistence of browser cookies/session tokens;
- code that disables TLS certificate verification for convenience;
- secret values committed to Git.

Any future execution feature would be a separate architecture phase with fresh legal/terms/security review.

## 3. Source terms boundary

Before enabling a persistent collector for a sportsbook, document:

- exact hostname/operator used;
- whether data access is public or authenticated;
- applicable terms/reference URL;
- any explicit automation/data-use restriction relevant to the planned mode;
- whether the collector only observes data generated by normal page access;
- architect decision approving the acquisition method.

Do not assume the rules of one Fonbet legal entity/domain automatically govern another.

At bootstrap, the international `fonbet.com` rules include restrictions on automated analysis in connection with making bets and on automated bet/request submission. Since MVP does not place bets, this does not by itself define the read-only collector outcome; it does mean we must keep observation and execution strictly separate and recheck the exact operator terms before persistent use.

Reference:

- https://fonbet.com/rules

## 4. Polymarket boundary

The initial connector uses public market-data endpoints/streams. No wallet/private key is needed for this MVP market-data path.

References:

- https://docs.polymarket.com/market-data/overview
- https://docs.polymarket.com/api-reference/wss/market

Do not introduce a wallet private key, Polymarket trading credentials or order-signing code into MVP configuration.

## 5. Secrets inventory

Expected MVP secrets may include only what the feature actually needs, primarily:

- Telegram bot token;
- Telegram destination/chat identifier where considered private;
- optional credentials for an architect-approved third-party data provider.

Potential browser session data is treated as secret/private even if not represented as an environment variable.

## 6. Secret storage

For local development:

- environment variables and/or an untracked `.env` file are permitted;
- `.env` is gitignored;
- provide `.env.example` with names/placeholders only;
- no secret in source code, config examples, tests or fixtures;
- no secret in screenshots committed to the repo;
- no secret in commit messages/issues.

If the project later runs as a long-lived Windows service, prefer Windows Credential Manager/DPAPI-backed secret handling or another architect-approved secret store rather than plaintext persistence.

## 7. Git secret gate

Before every push that touches acquisition/config/logging:

- inspect diff;
- run secret scan if configured;
- check for `.env`, cookies, browser databases, HAR files, network dumps and raw authorization headers;
- ensure runtime `data/`, `logs/` and `browser_profiles/` are ignored.

A detected credential in Git history is a security incident, not merely a cleanup task.

## 8. Logging redaction

Never log full values of:

```text
Authorization
Cookie
Set-Cookie
X-API-Key or provider equivalents
Telegram bot token
wallet/private keys
session/local-storage tokens
password fields
```

Network diagnostic loggers shall default to an allowlist of safe metadata rather than “dump every header then blacklist a few”.

## 9. Raw response/body handling

Some source bodies may contain identifiers or private/session-linked data even if the requested odds are public.

Rules:

- raw capture is opt-in/bounded;
- inspect content class before long-term retention;
- redact before persistence where practical;
- store runtime captures outside Git;
- sanitized fixtures contain only minimal fields necessary for deterministic parser tests.

## 10. Browser isolation

Use a dedicated browser context/profile for scanner diagnostics rather than the owner’s everyday profile whenever possible.

Do not:

- copy Chrome/Opera primary profile wholesale;
- export passwords;
- read unrelated tabs/cookies;
- browse outside task scope.

The scanner is not a general browser surveillance tool.

## 11. Local API exposure

Any FastAPI/control interface:

- binds to `127.0.0.1` by default;
- is not exposed to LAN/Internet by default;
- does not return secrets/raw session headers;
- separates health/read endpoints from any future mutating actions.

Remote exposure would require authentication/TLS/threat-model decisions.

## 12. File permissions

Runtime directories should be created under the owner’s user context. Secret/browser-profile files should not be intentionally made world-readable/shared.

Deploy keys/private SSH keys remain under the owner’s `.ssh` area, never under the repository workspace.

## 13. Dependency security

- Pin/lock dependencies reproducibly once the environment bootstrap is implemented.
- Do not install packages solely because a tutorial says so.
- Prefer maintained packages and official SDKs where appropriate.
- Record material dependency additions in review/handoff.
- Run dependency vulnerability scanning when CI is established.

## 14. Network safety

- TLS verification stays enabled.
- Timeouts are mandatory.
- Redirect behavior should be understood for collectors.
- Rate limits/backoff are respected.
- No scanning of arbitrary hosts.
- Source URLs/hosts are configuration/allowlist controlled.

## 15. Data minimization

The scanner needs market data, not user/account behavior. Do not collect unrelated personal information from source pages.

## 16. Telegram boundary

Telegram notifications contain market/opportunity data only. Do not include:

- secrets;
- full raw payloads;
- session data;
- local filesystem paths containing usernames if avoidable;
- account balances unless a future explicitly approved feature requires them.

## 17. Incident classes

At minimum:

```text
SECRET_EXPOSURE
ACCESS_CONTROL_BLOCK
TERMS_BOUNDARY_UNCLEAR
SOURCE_RATE_BLOCK
RAW_DATA_PRIVACY_RISK
UNEXPECTED_AUTH_REQUIRED
LOCAL_API_EXPOSURE
DEPENDENCY_SECURITY_FAILURE
```

Security incidents should stop the affected feature path until reviewed.

## 18. Compliance status labels

For each source acquisition method record one of:

```text
APPROVED_READ_ONLY
PROBE_ONLY
REVIEW_REQUIRED
BLOCKED
DISABLED
```

`PROBE_ONLY` does not authorize continuous production collection.

## 19. Owner actions

The owner, not Codex/ChatGPT, supplies and controls credentials and acceptance of third-party service terms. Agents must not invent consent or access rights.

## 20. Architecture invariant

Research data acquisition, opportunity analysis and any future trade execution must remain separable modules/process boundaries. No collector is allowed to “helpfully click” wager controls while reading odds.
